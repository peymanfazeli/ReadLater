# SETUP.md

## Scope

This setup is intentionally project-local. Do not alter shared or parent-level configuration.

All commands, generated files, configuration changes, and dependencies must remain within the project root. Do not modify parent-level Gradle files, shared build logic, global tooling configuration, or other projects.

## Before Creating the Project

Record the following versions in the project README or a project-local setup log:

- Node.js
- Package manager
- Java/JDK
- Android SDK and build tools
- React Native
- Android Gradle Plugin version generated by the selected template
- Gradle version generated by the selected template

Use the official React Native CLI template compatible with the selected environment. Do not manually copy Gradle files from another project.

Before initialization, verify:

- The intended project root is correct.
- The selected React Native template supports the installed environment.
- Required Android tooling is available.
- The project directory is dedicated to this application.
- No existing files will be overwritten unintentionally.

## Suggested Initial Sequence

1. Create or identify an empty, dedicated project directory.
2. Confirm the absolute path of the project root.
3. Verify that all intended destinations are descendants of the project root.
4. Initialize the React Native CLI project in that directory.
5. Record the generated versions and relevant environment details.
6. Run the default Android debug build before adding features.
7. Confirm that the baseline build succeeds.
8. Commit the clean baseline if version control is configured.
9. Add application code only after the baseline build succeeds.
10. Implement the MVP incrementally according to `PLAN.md`.

The project should be Android-first while keeping the structure reasonably compatible with potential future iOS support.

## Project Boundaries

All implementation and configuration changes must remain inside the project root.

Do not modify:

- Parent directories
- Parent-level Gradle or settings files
- Shared Gradle scripts or build logic
- Global Android Studio, Gradle, Java, Node.js, Git, or shell configuration
- Other projects
- Shared scripts or configuration files
- Files outside the project root

Before every write operation:

1. Inspect and confirm the absolute project root.
2. Resolve and verify the destination path.
3. Confirm that the destination is inside the project root.
4. Ensure that the operation does not overwrite unrelated files.
5. Avoid creating generated artifacts in parent directories.

If the correct project root cannot be verified, stop and report the blocker before writing files.

## Safety Checks

Before any write:

- Print or inspect the absolute project root.
- Verify that the destination is a descendant of the project root.
- Do not use parent directories for generated artifacts.
- Do not modify shared or global configuration.
- Keep `android/local.properties`, keystores, credentials, and secrets out of version control.
- Do not commit API keys, signing credentials, passwords, or other sensitive data.
- Review generated files before committing them.
- Do not delete or replace existing files unless the change is explicitly required and remains within the project scope.

## Environment and Dependency Policy

Use the package manager selected during project initialization consistently.

Before adding a dependency:

- Confirm that the existing React Native or Android platform capabilities are insufficient.
- Document the reason for the dependency.
- Verify compatibility with the selected React Native and Android versions.
- Prefer a maintained and minimal dependency.
- Avoid adding dependencies for functionality that can be implemented safely with existing platform APIs.
- Record dependency changes in the relevant project documentation.

Do not upgrade unrelated dependencies or tooling as part of a feature implementation unless required to resolve a documented blocker.

## Baseline Commands

Use the package manager selected for the project.

Typical command categories include:

- Install dependencies
- Start the development environment
- Typecheck
- Lint
- Run unit tests
- Run Android debug build

The exact commands must be recorded after project initialization. Do not guess command names, scripts, or build parameters.

Record the following for each baseline check:

- Command executed
- Execution environment, when relevant
- Result
- Relevant warnings or errors
- Any known limitations

A check must not be reported as successful unless it was actually executed and its result was verified.

## Android Build and Release Safety

For local Android development:

- Keep `android/local.properties` local and ignored.
- Do not commit keystores or signing credentials.
- Do not modify global Android SDK or Gradle configuration.
- Use project-local configuration wherever possible.
- Verify debug builds before attempting release builds.
- Document release-specific prerequisites in `BUILD_RELEASE.md`.
- Never claim release readiness without executing and recording the applicable checks.

## Troubleshooting

When a command fails:

1. Capture the exact command and error output.
2. Determine whether the issue is project-local or environment-related.
3. Prefer changes inside the project root.
4. Do not change global or parent-level configuration as a workaround.
5. Avoid unrelated upgrades or broad configuration changes.
6. Document unresolved issues and their impact.
7. Stop and report a blocker when resolving the issue requires unsafe operations, unavailable access, missing credentials, or changes outside the approved project boundary.

## Completion Criteria

The setup phase is complete only when:

- The project root has been verified.
- The React Native CLI project has been initialized using a compatible official template.
- Environment and generated tool versions have been recorded.
- The default Android debug build has succeeded.
- The baseline commands have been recorded.
- Sensitive and local-only files are properly ignored.
- No changes were made outside the project root.
- The clean baseline is committed when version control is configured.
